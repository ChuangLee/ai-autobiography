# mv/lab：纯代码 MV 的各场样片

《河水不回答》MV 的现行做法：全片由代码在浏览器里实时算出（只用 WebGPU），不用视频素材。每一场是一个独立网页，放在这里各自的文件夹里，原版审看地址是 https://blind.pub/zichengjing/mv/lab/ ，本分支对照入口是 https://blind.pub/zichengjing/mv/codex/ 。

**分镜以 `mv/重构设计.md`（第五版）为准**：第一节是用户历次提过的要求，第二节是原则，第四节是逐镜头分镜，第七节是用户批注的处理。动手之前先读它。`mv/分镜.md` 是 Veo 素材时代的旧分镜，已作废。

### 各场已知的问题（下一轮要改的）

- **第一段 `river`**
  - 金色巨像还不够大：用户要的是“画面装不下、俯视山河”。远景里看不到被它照亮的山和云，体量出不来；脸仍偏面具。
  - 河口（41.6–44.5）的字糊成一条浅带，认不出单个的字。
  - 山水长卷里五条河在远处只是灰带，看不出是字。
  - 分镜里的几处变形转场（烟升成鬼、眼洞合成石头、石影伸到河岸）只做了一半，接缝处仍靠叠化。
- **第二段 `windows`**
  - 水墨夜城近看仍像带晕染质感的三维渲染，不像笔墨。
  - 拉高时全城的火星流像烟花弧线。
  - 北斋的浪刚升起和拍下的瞬间形状不好。
  - 霍珀那一镜里人自己在玻璃上的倒影看不清。
  - 和第一段的衔接（“巨像身上的一个字亮成一扇窗”）没做，样片直接从窗开始。
- **第三段 `verse3`**（第一轮）
  - 没有出现人手：“一只手”只靠毛笔和它的影子表现；林觉民的信是自己写出来的，女孩只看得到她的网页。
  - 机房里的人远看可信，近看像电脑模型。
  - 镜头从皮影幕布上方绕到幕后，约 106.15 秒有一瞬侧对幕布，偏暗。
  - 皮影的雕刻像陕西样式，但不如真的华县皮影精细。
  - 诗云里很小的字看着像软的小方块。
  - 水没有折射，只在变白之前短暂像一层水。
  - 帧率风险最高的是机房（景深时每像素最多 9 次采样，人是光线步进的），掉帧时用 `spp=3` 或 `4`；手稿用 `dspp=2`；诗云用 `n=150000`。
- **间奏 `dive`**
  - 结尾的鹏仍偏平，像纹章，青绿山水层次不够。
  - 鲲变鹏那几秒机位贴得太近。
  - 正式配置（96 格、60 万字）下的字群和颜料只抽查过两三帧。
- **第四段 `verse4`**（第二轮）
  - 宋人山水的主峰改成范宽式的竖向石柱和雨点皴，但仍有点像梳齿，中景的山偏圆。
  - 未来主义的残影人物放大了，远岸的仍偏小，近岸的几串容易挤在一起。
  - 西斯廷的人手已按解剖重建，筋腱可能过于明显；裂缝打开时仍有一瞬像描黑边的格子。
  - 朱印的印文是制作方自己定的小篆“我”，待用户确认。
  - 和间奏结尾的衔接只对了配色，没有逐帧对齐。
- **各场之间**：交接时刻和画面都还没对齐，比如 `river` 结束于 56.0，`windows` 从 55.9 开始，前一场的最后一帧和后一场的第一帧并不相同。

### 还没决定的

### codex 的整片播放

`film/` 用同一条音轨贯穿 0–263.63 秒。它从歌曲时间选择序、字河、千窗、机房与手稿、间奏、第四段、桥段和高潮尾声。分界依次为 18.90、55.92、88.40、111.83、154.60、192.70、223.00 秒。`film/?from=时间` 从指定处起播，进度条和方向键可以跨场定位，`film/?t=时间` 可用于整片静帧检查。场景的画质参数也随链接传入。

每场仍可以独立打开。总播放器把当前场放在同源子页面里，调用其 `run` 暴露的绘制与定位方法。只有外层读取音频、响应播放手势、绘制歌词。距交界七秒开始预热下一场，最多同时保留两场。到交界时保留上一场的最后画面，下一场在 850 毫秒内溶入，随后释放旧 WebGPU 设备和页面。定位或补算较慢时歌曲暂停等待。连续拖动以最后一次松手的位置为准。

## 共用底座 `lib.js`

- `initGPU(canvas)`：WebGPU 设备；`?res=` 缩放分辨率。
- `Post`：HDR 目标、辉光、色调映射、颗粒、暗角、遮幅（`bars` 0 到 1）。
- `loadAtlas(device)`：`mv/glyphs/atlas.png` 里 962 个真字（甲骨到宋体、世界古今文字、各语言的词、符号），分组见 `info.groupRanges`，来源与许可见 `mv/glyphs/CREDITS.md`。
- `textTexture(device, w, h, draw)`：用浏览器字体把句子画进纹理。
- `run({ g, seg, scene, notes, captions, title })`：按歌曲时间播放一段，显示歌词和括号注释；`scene` 提供 `reset()`、固定步长 `step(dt, t)`、`draw(t)`；`?t=秒` 出静帧，`?from=秒` 从某处起播。

歌曲数据在 `mv/song.json`（句子时间来自 Suno 的逐字对齐，重音和响度从音频量出，由 `mv/song.py` 生成），音频是 `review/web/audio/v8-g-r3-1.mp3`，线上路径 `/zichengjing/audio/`。

没有 `step` 的镜头按歌曲绝对时间直接出画。粒子、流体镜头以每秒 60 步保持确定性，向后定位时从段首重算。播放中跳转会暂停音频、保留上一幅完整画面，分批补算，每批最多 24 步。目标画面和歌词就绪后再续播，中途再次跳转以最新位置为准。暂停停留在同一时刻不重复提交画面。

字库只需要一个灰度值来表示墨迹，上传后使用 `r8unorm`。4096² 字库和全部 13 级缩小纹理的像素数据合计 21.33 MiB，原先为 85.33 MiB。SwiftShader GPU 回读核对了所有级别的 22,369,621 个灰度值，完全一致。需要 CPU 读取笔画的首场仍可向 `loadAtlas` 请求保留原始位图。深度纹理只在镜头首次使用时创建，1080p 的纯色彩渲染因此可再省 7.91 MiB。

六层辉光由六次缩小、五次放大和最终合成组成。强度为零的水墨、版画镜头只执行最终合成。开启辉光时，只有变化的参数才重写对应的 GPU 缓冲。以相同场景代码在 Chrome SwiftShader 384×216 的实测为例，179.5 秒宋画的后处理从 12 道降至 1 道，163.5 秒青铜仍为 12 道。同一时刻复画时两者都只写一次后处理缓冲，两幅画面的截图分别与优化前逐字节相同。这组计数可在不同显卡上复查，实际播放帧率须在观看设备上测。

## 出静帧检查

```
cd mv/lab
node shot.mjs <场景文件夹> 30,41.5,48.7 --res 0.4 --out <输出目录> [--q "n=60000&grid=48"]
```

- 用的是无头 Chrome 加 SwiftShader 的软件 WebGPU，很慢；带模拟的场景每一帧都要从段首一步步算过来。检查时用 `--res 0.3` 到 `0.5`，并用 URL 参数调低粒子数和网格。**不要用 `--res 1`**，在这台机器上跑不完。
- 页面的 console 输出和着色器错误会打印出来。机器负载高时偶尔会读取失败，重试即可。
- 已知怪癖：在 `loadAtlas` 之后调用 `textTexture`，无头 Chrome 里可能卡住，所以先做文字纹理，再加载字形图集。
- 每场的质量参数写在该场 `index.html` 开头的注释里。例如 `river` 的 `n`（粒子数）、`grid`；`dive` 的 `grid`、`n`、`steps`；`windows` 的 `steps`、`n`。`verse3` 用的字体是项目字体的子集，放在 `verse3/fonts/`，改了画面里的文字要重跑 `python3 fonts/make.py`。
- `shot.mjs` 被杀掉或超时（`--limit` 分钟，默认 40）时会连带关掉它开的 Chrome。
- 等静帧跑完时不要写 `until ! pgrep -f "shot.mjs ..."`：`pgrep -f` 会匹配到这条等待命令自己，永远等不完。直接在前台跑，或者等它的输出文件。

## 做法上的约定

- 画面里的字和诗都是真的：单字取自字形图集，句子用真实字体排。
- 不频闪、不撕裂、不在明暗差很大的画面之间硬切。镜头之间是有来由的连续变形，0.8 到 1.5 秒。
- 一切都是时间或固定步长状态的函数，保证 `?t=` 的静帧和播放时一致。
- 不再用的镜头不要删，存档备用（见 `river/archive.js`、`windows/archive/`、`dive/archive.js`）。
- 不在这台服务器上渲染成片（4 核、7 GB 内存、磁盘接近满）。成片靠网页在观看者的显卡上实时合成。

### codex 分支的线上对照

本分支只用 `bash mv/lab/deploy.sh` 发布精修分镜、八场代码画面及全片播放器。对照入口 https://blind.pub/zichengjing/mv/codex/ ，两列链接取同一首歌的同一时刻。原版在同级的 `lab/`，共享字库与音频。codex 分镜在 `design-codex/` 的第八节，批注的 doc 为 `mv-design-codex`。原版已有的五场可从表中 18 个时刻对读，新增段落可从页首进入。

### 巨像的角色试稿

角色页 `portrait/` 可以同角度对照三种画法。`portrait/planes-shot.html` 用原声播放 44.58–55.92 秒的雕塑稿。另有一套依据通用人脸地标重画的几何与目光，由 `film/?portrait=anatomy` 带进序、字河、千窗和高潮。第四稿的曲面系数可以用 `portrait/tools/fit_contours.py` 从许可文件指定的地标重建。网页上的 WebP 是浏览用实帧，正片与转面各自实时绘制。

“河岸上的目光”使用 Lee Perry-Smith 授权的扫描曲面和程序绘制的眼睑、眼球、水面与字流。原始数据出处和改编记录在 `portrait/scan-source.txt`。从 `film/?portrait=sitter&from=44.58` 连看前后两场；单独看 `portrait/sitter.html`，加 `?head=cage` 可用相同摄影机看手塑细分稿。该机位沿颊侧“口”的内白进入 55.92 秒的同一间屋。

### codex 全片实作与检查

- 全片入口 `film/` 用同一音轨从 0 播至 263.63 秒。序章、第一段、第二段、第三段、间奏、第四段、桥段、尾声依次在 0、18.9、55.92、88.4、111.83、154.6、192.7、223 秒交接。用 `film/?from=秒` 定位。低分辨率检查全片时可用 `res=.25&riverGrid=.125&diveGrid=20`，分别指定字河的网格倍率和水下的网格边长。播放器预备下一场，交接后释放旧场的 GPU 设备。
- 序章的毛笔写出“字”，墨里分别出现正文的巨像曲面、诗云和鹏翼，末帧使用第一段的岩画。桥段从草坡上的两代人走向金箔衣袍与飞白。高潮沿同一图景换十种画法，末卷收回第二段的夜城。尾声引用桥段末笔的实时绘制代码。
- 从对照页可以单独对读，也可以用 `river/?join=1&from=41.6` 连看两场。镜头从巨像颊上的楷书“口”进入夜城，交接处使用第二场同一相机实际画出的窗。两场共用 WebGPU 设备、音频时钟、字库和后处理。
- 巨像的脸和窗中人的头肩来自同一组曲面。巨像像素用曲面求交，身体周围的字流使用启动时烘出的 72×120×48 距离及法线体积。窗内聚散的字只在初始化时投影到人物表面，两户和玻璃里的倒影复用这组顶点。
- 第一段石刻、竹简、泥板与碑拓上的笔画从真字图集取样。水墨长卷根据相机张角、距离和实际渲染高度选择字形纹理层级。字河的初始粒子使用固定种子。
- 低清静帧用来检查造型、着色器编译和段落交接。低粒子数或从中段起算的图只用于定位问题。观众设备的帧率与长时间运行的显存占用仍待实测。
